# Town Meeting Manager — Revival Audit (2026-08-25)

*Synthesis of ten dimension audits plus an adversarial verification pass over every critical and high claim. Findings that failed verification have been dropped; overstated ones are corrected inline and marked. Nothing here is asserted without a file, line, or command behind it.*

---

## Bottom line

The staff-facing core of this product is real and in places genuinely good — a clerk can build an agenda from a template, run a live meeting with attendance, quorum, motions, roll-call votes, executive session, recusal and adjournment, and generate deterministic minutes. `packages/shared` is a real contract layer, the Maine notice-rules engine is honest and tested, and the relational model is shaped correctly for public records. That work is worth preserving.

Everything wrapped around that core is either broken or unverified. Authorization does not function: the JWT hook never emits a `permissions` claim, RLS looks up permissions by action **code** while the app writes them by action **name**, and the API reads `payload.role` which Supabase always sets to `"authenticated"`. The net effect is a two-tier system — `role='admin'` can do everything, everyone else can do almost nothing — plus a privilege-escalation path through self-writable `user_metadata`, plus an RLS policy that lets a self-onboarded admin rewrite their own `town_id` and take over any other town. Six API endpoints are unauthenticated and internet-reachable, one of which will render attacker-supplied HTML into email sent from a town's own verified domain.

`supabase/migrations/` cannot build a working database. The `invitation` table, the notification retry columns, and `user_account.email` / `display_name` exist only in a hand-applied dev volume — the last three have **no SQL source anywhere in the repo**. The public portal, the entire reason a town buys this, cannot be turned on at all (`town.subdomain` is never written by any code path) and would render empty if it were (seven wrong column and bucket names in `portal.ts`).

None of this was caught because there is no CI, no linter, no typed Supabase client, no route tests, and a test suite whose Supabase mocks make `.eq()` an identity function. The green build is not evidence.

This is roughly two to three months from a defensible pilot, and the highest-value fixes are small and concentrated.

## Blockers before a pilot town

### 1. Cross-tenant takeover: any signed-up user can become admin of any town
**Evidence.** `supabase/migrations/20260310000002_rls_onboarding_inserts.sql:14-16` — `CREATE POLICY user_account_update_own ON user_account FOR UPDATE TO authenticated USING (person_id = auth.uid());` No `WITH CHECK`, no column restriction, so `town_id`, `role` and `permissions` are all self-writable. The predicate is satisfiable because `20260310000003_onboarding_rpc.sql:104-113` sets both `person.id` and `user_account.person_id` to `auth.uid()`. The new `town_id` propagates into the JWT on next refresh via `20260308000038_create_custom_access_token_hook.sql:66-72`. Victim town UUIDs are handed out by the unauthenticated `GET /api/portal/resolve` (`packages/api/src/routes/portal.ts:67`), and signup is open (`infrastructure/docker-compose.production.yml:128`, `.env.production.example:38`).
**Why it blocks.** Full read/write over another town's `person` records, executive sessions, draft minutes, motions and vote records — reachable from an anonymous starting point. Every town on the platform is exposed to every other town.
**Effort.** M

### 2. Six unauthenticated internet-reachable API endpoints, one of which is a phishing platform
**Evidence.** `packages/api/src/routes/notifications.ts` registers with no `preHandler` at lines 164, 193, 216, 237, 249 (admin routes, service-role client, **no `town_id` filter** — `/admin/notifications/bounces` returns every bounced user's id, email and display name platform-wide; the DELETE clears suppression on a caller-supplied `:userId`), and line 355-366 `POST /notifications/events` which takes `{event_type, town_id, payload}` from the body and fans it out. `packages/api/src/templates/email/admin-alert.hbs:14` renders `{{{alertMessage}}}` as a raw triple-stash. Mail is sent from `Town of X <notifications@x.townmeetingmanager.com>` (`invitations.ts:143-144`). `infrastructure/nginx/nginx.conf:236` proxies all of `/api/` on every town subdomain with no path filtering and no `limit_req` anywhere. The push routes in the *same file* (`:281`, `:318`) do call `await app.verifyAuth(...)`, so this is an oversight, not a design.
**Why it blocks.** Unauthenticated cross-tenant PII disclosure, plus turnkey phishing at municipal officials wearing the town's own DKIM signature. Fix this *before* repairing the notification pipeline — repairing recipients first turns a dormant hole into a live one.
**Effort.** M (S for the nginx stopgap)

### 3. Authorization is inert: only `role='admin'` can do anything, and `user_metadata` is an escalation path
**Evidence.** Three divergent implementations (`packages/shared/src/utils/permissions.ts`, `packages/web/src/hooks/usePermission.ts`, `packages/api/src/plugins/auth.ts`) all read a `permissions` claim the hook never issues (`20260308000038:76-94` injects only `town_id`/`app_role`/`person_id`/`user_account_id`). Separately, `buildPermissionsFromTemplate` (`packages/shared/src/constants/permissions.ts:236-244`) writes the matrix keyed by action **name** (`edit_agenda`), while every RLS caller queries by **code** — `has_permission('R1')` ×4, `'M3'` ×4, `'A3'` ×4, `'C2'` ×3, `'M2'` ×2, `'A2'` ×2, `'R4'`, `has_board_permission('A1')` ×2, `('M1')` — against `20260308000027:96` `RETURN COALESCE((user_permissions ->> action_code)::BOOLEAN, false)`. `has_permission` returns true for `admin` and **false for `sys_admin`** (`:77-84`). API side: `packages/api/src/plugins/auth.ts:103-107` reads top-level `payload.role`, which the migration's own comment (`:74-81`) says is always `"authenticated"`, so the admin bypass at `:147` never fires and `:151` checks an empty object → 403 on `documents.ts:86,269` and `minutes.ts:82,269,433,596,647`. And `auth.ts:116-120` falls through to `payload.user_metadata.permissions`, which any user can self-write via GoTrue.
**Why it blocks.** Only `role='admin'` can open the live meeting screen (`live.tsx:1160` hard-blocks). The Town Clerk — a `staff` account, the actual operator this product is sold to — is locked out of the core screen. Every PDF-producing endpoint 403s for everyone. Simultaneously, any authenticated user can grant themselves every permission.
**Verifier's decisive datum:** `supabase/seed.sql:92` seeds permissions keyed by **codes** (`{"A1": true, "A2": true, ...}`). The repo contains both conventions in its own source of truth, and the seeded shape is the only one RLS can read. Standardize on codes.
**Effort.** L

### 4. `supabase/migrations/` cannot build a working database
**Evidence.** `migrate.sh:23` iterates `supabase/migrations/*.sql` only. `CREATE TABLE invitation` exists **only** in `docker/migrations/012_invitation_email.sql:13`, referenced by nothing in `infrastructure/`. `email_bounced`/`email_complained` and their timestamps exist only in `docker/migrations/011:142-145`. `notification_delivery.retry_count`, `next_retry_at`, `postmark_message_id`, `sent_at`, `opened_at` appear in **no `.sql` file anywhere in the repo**. `user_account.email`, `display_name` and `notification_preferences` also have **no SQL source anywhere** — they exist only in the running dev volume and in the generated `database.ts`. Two storage buckets (`exhibits`, `minutes`) are never created; only `documents` is (`20260311000003:8-10`).
**Why it blocks.** A fresh deploy yields a product where invitations fail (nobody can be onboarded past the first admin), every notification silently resolves to zero recipients, exhibit upload fails with "Bucket not found", and both portal PDF endpoints 500. Part of the schema has no artifact at all — losing the ~111 MB dev volume loses it permanently.
**Effort.** M–L (L if the volume is gone)

### 5. The public portal cannot be turned on, and would render empty if it were
**Evidence.** Grepping `packages/web/src` and `packages/api/src` for `subdomain` returns **only reads** — no input, no mutation, and `completeWizard.ts:53-79` does not pass it to `complete_onboarding`. So `portal.ts:66-68`'s `.eq("subdomain", subdomain)` can never match. On top of that, `portal.ts` queries five columns that do not exist: `agenda_item.item_type` and `duration_minutes` (`:254`; real names `section_type`, `estimated_duration`), `exhibit.file_url` (`:268`; real name `file_storage_path`), `board.meeting_schedule` and `quorum_custom_value` (`:468`), `person.first_name, last_name` (`:493`; the column is `name`) — and reads PDFs from a nonexistent `minutes` bucket (`:388`, `:426`). Errors are discarded, so published agendas return `sections: []` and every board page 404s. `packages/web/src/portal/pages/MeetingDetail.tsx:42-53` also keys status labels on `scheduled|in_progress|completed|cancelled` against a DB enum of `draft|noticed|open|adjourned|minutes_draft|approved|cancelled`, printing raw `minutes_draft` to residents.
**Why it blocks.** Job 5 — the public finds the meeting, agenda and minutes — is 0% functional. This is the demo that ends the pilot, and it is what residents see, not what the clerk sees first.
**Effort.** M

### 6. Backups exclude every generated PDF; no restore has ever been tested
**Evidence.** `infrastructure/scripts/backup.sh` runs exactly two `pg_dump` commands and never touches the `storage-data` volume; `restore.sh:37-38` runs only `pg_restore`. All PDFs — agenda packets (`documents.ts:225`), meeting notices (`:329`), minutes (`minutes-pdf.ts:57`) — live in the file-backed `documents` bucket on that volume. No WAL archiving despite `docs/advisory-resolutions/3.2-supabase-hosting.md:40` requiring PITR. Backups are unencrypted, on the same host, with no offsite copy.
**Why it blocks.** A DB-only restore returns rows whose `pdf_storage_path` points at files that no longer exist — every portal document link 404s while the app reports them generated. Maine records-retention obligations are not met by "we restored the database." RPO is up to 24 hours: a crash at 01:59 loses an entire evening's select board meeting.
**Effort.** L

### 7. Nothing can alert a human, and the email pipeline is already failing silently *in dev*
**Evidence.** `docs/deployment.md:152` prescribes `*/5 * * * * ... ./health-check.sh >> /var/log/tmm-health.log 2>&1` — both streams redirected, so cron has no output to mail and a non-zero exit alone triggers nothing. No `@sentry` in any package.json despite `docs/advisory-resolutions/1.3a-frontend-architecture.md:295-297` calling it essential. No uptime probe, no log aggregation, no rotation. Meanwhile `packages/api/src/services/notification-service.ts:45-49` selects `board_member.user_account_id` — **a column that exists in no migration and not in the dev DB either** — and `:58`/`:72` destructure only `{ data }`, discarding the error, returning `[]`. **Board-scoped notifications resolve to zero recipients on the developer's own machine today.**
**Why it blocks.** This is precisely the "meeting notice stops sending and nobody finds out" scenario, and it is the current default state. `docker inspect` shows healthy, `/api/health` returns 200, and no email leaves the box.
**Effort.** M

### 8. Motion tallying is wrong in two ways, with zero tests
**Evidence.** `packages/web/src/hooks/useVoteCalculation.ts` has no test file. `calculateVoteResult(votes, requiredMajority = "simple")` computes a two-thirds threshold at `:80`, but both call sites pass one argument — `VotePanel.tsx:167` and `:197` — so **every board is tallied as simple majority regardless of its configured quorum/majority rule**, and the result is written straight to `motion.status` and `motion.vote_summary` (`VotePanel.tsx:231-233`). Separately `:104-110` returns "Passed unanimously" whenever `nays === 0 && yeas > 0`, ignoring abstentions, recusals and absences — while the API formatter (`minutes-formatters.ts:116`) correctly requires all four to be zero. A 3-0-2 vote reads "Passed unanimously" on the clerk's screen and "Passed 3-0, 2 abstaining" in the PDF.
**Why it blocks.** A supermajority motion can be recorded as passed on a bare majority, in the legal record, published to the portal. The clerk reads the wrong result aloud in a public meeting.
**Effort.** M (S for the unanimity fix)

### 9. `push_subscription` has RLS never enabled
**Evidence.** `supabase/migrations/20260313000003_push_subscriptions.sql` contains no `ENABLE ROW LEVEL SECURITY` and no `CREATE POLICY`; it is the only one of 26 tables missing from the enable sweep. It holds `endpoint`, `p256dh` and `auth` (`:6-11`) — the complete Web Push credential set.
**Why it blocks.** Any authenticated user can read every push credential platform-wide and push arbitrary notifications to any official's device, or delete all rows to disable push entirely.
**Effort.** S

### 10. The meeting record cannot be corrected, and adopted minutes can be silently rewritten
**Evidence.** `routes/meetings.$meetingId.review.tsx` is 1,300 lines with **zero** write calls (`grep -c '\.update(|\.insert(|\.delete(|useMutation'` = 0), and `live.tsx:1151-1157` redirects away once status is `adjourned`. A mis-tapped vote or attendance entry is frozen permanently. Meanwhile `minutes_document` UPDATE is gated on `town_id = get_current_town_id() AND has_permission('R1')` with no status predicate (`20260308000034:38-42`), and `minutes.tsx:277-283` updates `content_json` with no status check — so an **admin** (corrected from the original "any R1 holder" — see Verification notes) can rewrite adopted minutes via PostgREST. `audit_log` has **zero** references in either package. `minutes_addendum` (shipped with three RLS policies in `20260313000002`) has **zero** references anywhere — the only sanctioned amendment path does not exist.
**Why it blocks.** A town attorney will ask about this in procurement. An adopted public record that is mutable, unaudited, and un-amendable is the inverse of the product's premise.
**Effort.** L

## Findings by theme

### Theme A — Authorization and tenant isolation are structurally broken

**A1 · CRITICAL · One permission claim, two opposite consequences.**
`packages/api/src/plugins/auth.ts:116-120` resolves permissions as `payload?.permissions ?? payload?.app_metadata?.permissions ?? payload?.user_metadata?.permissions ?? {}`. The hook emits neither of the first two, so honest users land on `{}` → **403 on every gated route**, while `user_metadata` is self-writable via `supabase.auth.updateUser({ data: { permissions: {...} } })` → **full escalation for anyone who tries**. Two dimension audits each reported half of this; both are true of the same line.
*Impact.* Every PDF and minutes endpoint is dead for real users and open to anyone who reads this file.
*Fix.* Delete the `user_metadata` fallback from `auth.ts` and `useCurrentUser.ts`; change the `role` default from `"admin"` to deny; read the app role from `payload.app_role ?? payload.app_metadata.role` filtered through a `VALID_ROLES` set (the pattern already exists at `useCurrentUser.ts:95-99`); resolve permissions server-side from `user_account` rather than from the token. **Effort M.**

**A2 · CRITICAL · Codes vs. names — the 30-action matrix never matches.** See Blocker 3. Standardize on **codes** (RLS is the harder half to change, and `seed.sql:92` already uses them), add a shared test asserting every string passed to `has_permission` in `supabase/migrations/` is a member of `ALL_PERMISSION_ACTIONS`, and write a data migration rekeying any existing `user_account.permissions` blobs. **Effort L.**

**A3 · CRITICAL · Three RBAC implementations that disagree.** `shared/utils/permissions.ts:39-50` (admin-only bypass, denies `sys_admin`), `web/hooks/usePermission.ts:63-121` (grants `sys_admin`, always-allows V1–V5, lets board members inherit JSONB extras), `api/plugins/auth.ts:139-152` (flat `permissions[action]` lookup against a nested `{global, board_overrides}` structure). Home/meetings/people use one; live/review/minutes use the other. `requirePermission(action: string)` is untyped, which is how `minutes.ts:647` gates on `"approve_minutes"` — a string that is not one of the 30 defined actions. `components/auth/PermissionGate.tsx` has 37 passing tests and is rendered by nothing.
*Fix.* Collapse to `shared/utils/permissions.ts` as the single source (absorb `checkPermission`'s sys_admin, view-action and board-inheritance rules), make `usePermission` a thin wrapper, type `requirePermission(action: PermissionAction)`, and either wire `PermissionGate` everywhere or delete it with its tests. Replace `test/mocks/auth-mock.ts:52-64`'s synthetic matrix with a real decoded-JWT fixture. **Effort L.**

**A4 · CRITICAL · `user_account_update_own` cross-tenant takeover.** See Blocker 1. Additionally: stop returning `town.id` from `/api/portal/resolve`, and set `DISABLE_SIGNUP=true` with operator-provisioned towns. **Effort M.**

**A5 · CRITICAL · Six unauthenticated routes + unauthenticated Postmark webhook.** See Blocker 2. The webhook (`notifications.ts:44-46`) declares `{ config: { rawBody: true } }` but `fastify-raw-body` is not a dependency and `rawBody` appears nowhere else — signature verification was intended and never built. Chained with the unauthenticated `/admin/notifications/events/:id/deliveries`, delivery IDs become enumerable and a forged HardBounce permanently suppresses a specific official's meeting notices. **Effort M.**

**A6 · HIGH · `push_subscription` has no RLS.** See Blocker 9. Note `notifications.ts:296` writes `user_account_id: request.user.id` using the *auth* user id, so fix that identifier mismatch in the same change or the new policy predicate will not match. Add a CI check against `pg_tables.rowsecurity` so the next table cannot repeat this. **Effort S.**

**A7 · HIGH · `handle_new_user()` links invited accounts by email with no town scope.** `20260308000037:34-39` — `WHERE p.email = NEW.email AND ua.auth_user_id IS NULL LIMIT 1`, no `town_id` predicate, no `ORDER BY`. `person_email_unique_per_town` (`20260308000003:22`) deliberately permits the same email in multiple towns. Maine towns share regional staff; a contracted clerk with pending invites in two towns gets permanently bound to an arbitrary one, and recovery requires `auth.users` surgery.
*Fix.* Match on `user_account_id` or the invitation token passed through `raw_user_meta_data`; if email matching must remain, scope it by town and raise on ambiguity. **Effort M.**

**A8 · HIGH · Every SECURITY DEFINER helper runs with a mutable `search_path`.** All six/seven helpers in `20260308000027` (lines 21, 31, 41, 51, 61, 98, 151) plus `handle_new_user` and `custom_access_token_hook` lack `SET search_path`; only `complete_onboarding` (`20260310000003:41`) is hardened. `has_permission` does an unqualified `FROM user_account` read at `:88-90`. Not independently exploitable today — no PostgREST-reachable arbitrary-SQL path was found — but it is the containment boundary that converts any future medium bug into total RLS bypass, and Supabase's own linter flags it.
*Fix.* `SET search_path = public, pg_temp` on all nine, schema-qualify the reads, and demote the four claim-readers to `SECURITY INVOKER`. Add a migration-lint test. **Effort S.**

**A9 · HIGH · The `documents` bucket is public, so every draft agenda packet is world-readable.** `20260311000003:8-10` inserts it with `public = true`; the SELECT policy six lines below is dead for reads. `documents.ts` persists `getPublicUrl()` output into `meeting.agenda_packet_url`, and paths are `{town_id}/meetings/{meetingId}/...-{timestamp}.pdf` with both UUIDs discoverable from the public portal API.
*Fix.* Flip to private, serve via short-lived signed URLs gated on publication state, store the storage path rather than the URL, and add a UUID segment to the path. Note the portal's existing `createSignedUrl` calls sign against the nonexistent `minutes` bucket and must be repointed at `documents` in the same change. **Effort M.**

**A10 · MEDIUM · One Zod schema across five route files; zero JSON schemas.** `grep "z.object|safeParse|schema:" packages/api/src/routes/` returns three hits, all in the push-subscription block. `POST /api/invitations/accept` reads `password` with only a truthiness check before `supabase.auth.admin.createUser` — the client-side `signupSchema` (`routes/signup.tsx:30`) is trivially bypassed. Unvalidated `payload` is what makes A5's phishing vector arbitrary. Also: `invitations.ts:22` hard-codes `APP_SECRET = process.env.APP_SECRET ?? "default-secret-change-in-production"`, used to HMAC unsubscribe tokens, and `:488` interpolates the token-derived `eventType` unescaped into an HTML response.
*Fix.* `fastify-type-provider-zod` on every route reading body/params/query, reusing the shared schemas. Change the `APP_SECRET` fallback to a startup assertion that throws. Escape `:488`. **Effort M.**

### Theme B — The repo does not contain the database the app runs on

**B1 · CRITICAL · Missing tables, missing columns, missing buckets.** See Blocker 4. Three additional identifier-conflation defects belong to the same class:
- `notification_delivery.subscriber_id` is `UUID NOT NULL REFERENCES person(id)` (`20260308000019:12`), but `notification-service.ts:275` inserts a `user_account.id`. Every delivery insert violates the FK.
- `request.user.id` is the `auth.users` id but is written into `minutes_document.created_by` (`minutes.ts:222`), `push_subscription.user_account_id` (`notifications.ts:296`) and used to look up the inviter (`invitations.ts:113,249`) — all of which reference `user_account(id)`. **Why this was never caught:** `complete_onboarding` sets `user_account.id = auth.uid()` (`20260310000003:106`), so for the developer's own account the two coincide; `AddPersonDialog.tsx:114` generates a fresh UUID for invited accounts, so they diverge and the FK fails.
- `meeting.recording_secretary_id` is written as a *person* id (`MeetingStartFlow.tsx:185`) and read as a *board_member* id (`minutes-assembler.ts:369,481`). The column was added with **no FK at all** (`20260311000004:92`) while its sibling `presiding_officer_id` at `:89` got one, so the comparison silently never matches.
*Fix.* Dump the live dev schema, diff against a DB built purely from `supabase/migrations/`, and write catch-up migrations. Add `userAccountId` to `RequestUser` from `app_metadata.user_account_id` and audit every `user.id` usage. Decide whether the recording secretary is a person or a board member, then add the FK. **Effort L.**

**B2 · HIGH · The generated `Database` type is exported and imported by nothing; both clients are untyped.** `packages/web/src/lib/supabase.ts:21` and `packages/api/src/plugins/supabase.ts:13,25` both use the bare `SupabaseClient`. `grep -rn "Database" packages/web/src packages/api/src` (excluding `DatabaseError`) returns **zero** hits against a 3,175-line generated file. Consequence: 243 `.from()` call sites across 69 files are `any`, plus 237 `Record<string, unknown>` casts and 44 `as unknown as` casts.
*This is the single highest-leverage fix in the codebase.* Wiring `createClient<Database>()` would catch, in one pass: `board_member.user_account_id`, all seven `portal.ts` column/bucket errors, `notification_delivery.retry_count`, `user_account.email`, and the shape collisions in Theme C. It would **not** catch `auth_user_id: ""` (the generated type is `string | null`).
*Fix.* Type both clients; work the error wave down module by module, deleting casts. Add `pnpm db:types` + `git diff --exit-code` to CI so the type cannot drift from the migrations again. **Effort L.**

**B3 · HIGH · `board_member_unique_active UNIQUE (person_id, board_id, status)`.** `20260308000006:22` — because `status` is a key column rather than a partial-index predicate, a person who serves, is archived, and is re-elected to the same board **cannot be archived a second time** (`MemberArchiveDialog.tsx:75-79` is a plain status flip). The §2605 staff conversion is worse: `MemberTransitionDialog.tsx:207-211` bulk-archives across every board and fails entirely if any prior archived membership exists. This is the normal life cycle of a Maine select board seat.
*Fix.* `CREATE UNIQUE INDEX board_member_one_active ON board_member (person_id, board_id) WHERE status = 'active';` and drop the constraint. Gets more expensive with every town onboarded. **Effort S.**

**B4 · HIGH · Four code paths insert `auth_user_id: ""` into a UUID column.** `AddPersonDialog.tsx:123`, `AddMemberDialog.tsx:337` and `:447`, `MemberTransitionDialog.tsx:236`. The column is `UUID UNIQUE REFERENCES auth.users(id)` and its own comment says NULL is the intended value (`20260308000004:23,32`). *Unverified against a live database* (Docker unavailable in both audit environments) — `''::uuid` raises 22P02 by Postgres semantics, and no intervening layer coerces it. If it throws, every staff-account creation path in the product fails, including the People directory shipped in the most recent commit.
*Fix.* Change all four to `null`, then manually exercise "add a staff person and send an invite" against a real database before any release. **Effort S.**

**B5 · HIGH · Eighteen tables have no DELETE policy; client `.delete()` calls silently no-op.** Only `agenda_template`, `executive_session`, `future_item_queue`, `guest_speaker` and `permission_template` have one. The damaging case is `VotePanel.tsx:209-214`: delete-then-insert on re-vote, where `if (deleteError) throw deleteError` can never fire, immediately followed by inserts colliding with `vote_record_unique_per_motion` (`20260308000010:20`). A clerk correcting a mis-tapped vote gets a raw 23505 on the highest-stakes screen. Agenda item and exhibit deletes appear to work and reappear on refetch.
*Fix.* Upsert on `(motion_id, board_member_id)` for votes — it preserves the record rather than destroying it. Add DELETE policies for `agenda_item`/`exhibit`, or remove the delete UI. Assert on the returned `count` for every client delete. **Effort M.**

**B6 · MEDIUM · Column defaults disagree with app enums, so a town's first boards carry invalid values.** `20260310000001:36,42` set `quorum_type TEXT DEFAULT 'majority'` and `motion_display_format TEXT DEFAULT 'formal'`; neither value exists in `packages/shared/src/constants/enums.ts:232-245`, neither column has a CHECK, and `complete_onboarding` never sets either (`20260310000003:74-96`). `calculateQuorum` (`quorum.ts:32-44`) has no `'majority'` case and falls through to `default:` — which happens to match simple majority today, which is exactly why it will survive until someone edits that branch. `EditBoardDialog.tsx:91`'s `?? ## Verification notes

**Method.** Ten dimension audits produced ~120 findings. Every critical and high claim was re-derived independently from source by a verification pass. 63 verdicts were returned.

**Dropped — 1 claim.**
- ~~"Turbo's build cache key ignores `VITE_*`, so `deploy.sh` can ship a bundle pointed at the wrong Supabase instance"~~ (rated critical). **REFUTED experimentally.** Turbo 2.8.14 detects `framework: vite` and auto-infers `VITE_*` into the hash: `VITE_SUPABASE_URL=http://aaa.test` → `1f6e024c20b7ea6b`, `=http://bbb.test` → `238f0b6f15949680`; different. The dry-run reports `environmentVariables.inferred = ['VITE_SUPABASE_URL=<sha>']`, not the empty array originally reported. Since `deploy.sh:28` sources `.env.production` with `set -a`, those values are in the shell env and are hashed — rotating the anon key produces a cache miss and a correct rebuild. **Residual, minor:** `packages/web/.env` is not a declared task input, so a change made only in that gitignored file without exporting the variable would hit a stale cache. That is a local-dev footgun, captured in G14, not a production risk. The Dependencies dimension score was raised from 42 to 55 accordingly.

**Corrected — 6 claims.**
1. **"Any user holding R1 can rewrite adopted minutes."** Because `has_permission` looks up codes against a name-keyed matrix, `has_permission('R1')` returns true only for `role='admin'`. Corrected to: *an admin* can silently rewrite adopted minutes with no audit trail — and no non-admin can edit even *draft* minutes. Severity unchanged; the compliance argument is unaffected.
2. **"There is no `approved_by_motion_id` column and no linkage."** The column has existed since day one (`20260308000014:20`) and `live.tsx:727` writes it during the live meeting. Corrected to: there are **two** approval paths — a motion-linked client-side one (unguarded, duplicable) and a motion-less `POST /minutes/approve` which *does* check `status === 'review'` and 403s today.
3. **"Exactly one production file checks `isError`."** Three do (`NoticeTemplateEditor.tsx`, `MinutesWorkflowEditor.tsx`, `settings.minutes-workflow.tsx`), against 62 files calling `useQuery` (not 104). The finding stands; the numbers are corrected.
4. **"The permissions claim always resolves to `{}` → 403 for everyone."** True for honest users, but `auth.ts:116-120` falls through to self-writable `user_metadata`, so the same line is simultaneously a hard 403 and an escalation vector. Both consequences are now stated together (A1).
5. **"Minutes workflow buttons are dead for everyone including admins."** Five buttons (Edit, Submit, Regenerate, Publish, Export) are dead for everyone; Approve / Return for Amendments / Unpublish are gated on `isAdmin` and do render for admins. The workflow is still unusable end to end.

## Open decisions for the owner

These require product judgment, not engineering analysis, and the new master plan cannot be written without them.

1. **Hosting model: self-hosted single box vs. managed.** Choosing Supabase Cloud + a managed container host deletes or dramatically shrinks G1, G3, G4, G5, G6, G9 and G10 outright. This is the single largest scope decision in the audit.

2. **Permission model: codes or names; JWT or server-resolved; and who operates a live meeting.** Standardizing on codes is a one-line change per RLS caller plus a data migration; names means rewriting 21 policies. Putting permissions in the JWT makes them stale until refresh (a permission revoked mid-meeting stays active); resolving server-side is safer but costs a round trip for UI gating. And today only `role='admin'` can open the live screen — if the Town Clerk is meant to be `staff`, that is a product-shape decision that must precede the rebuild.

3. **Is FOAA notice compliance a product claim?** If yes: build the publish-to-portal flow, remove the manual Kanban shortcut, collapse the duplicate timestamp columns, and add seal/agenda/ADA contact/citation/posting locations to the notice PDF. If no: delete three dead columns and advisory 3.4 §3.2–3.3, and stop claiming it in README and any MMA materials.

4. **Is "AI minutes" the promise?** The database currently labels Handlebars output as `generated_by: 'ai'` while README markets Claude-drafted minutes as a paid feature and the clerk's live notes are silently discarded. Options: (a) build the Claude enrichment stage at the existing seam and render `operator_notes` first; (b) reposition as deterministic assembly and fix the flag today (one line now, a backfill migration later). Either way the flag must change before more records accumulate — and note there is currently **no narrative input at all**: no transcript, no audio, and `operator_notes` unrendered.

5. **Pilot scope: which of the seven jobs are in the contract?** Annual Town Meeting is offered as a meeting type with a 14-day notice rule but has no warrant, no articles, and votes castable only by seated board members. Resident subscription does not exist in any form. Data export does not exist. This needs to be settled in the pilot agreement, not discovered in March.

6. **Schema recovery: can the dev volume still be dumped, and is the repo the source of truth going forward?** If the ~111 MB volume survives, Blocker 4 is a dump-and-diff (M). If it is gone, `invitation`, the six `user_account` email columns and the five `notification_delivery` retry columns must be reconstructed from application code (L). Either way: has *any* database ever been built from `supabase/migrations/` alone, or has the dev DB always been the artifact? That answer determines whether the 15.02 deploy scripts need a rehearsal or a rewrite.

7. **Legal posture on the record: correction, amendment, custody and retention.** Should adopted minutes be blocked at the database level with `minutes_addendum` as the only sanctioned path? Should mis-recorded votes and attendance be correctable post-adjournment with an audit entry, or frozen? Who is legally the custodian — the town or you as operator — and what recovery point is acceptable to sell (advisory 3.2 promised PITR; the build did not deliver it)? Locking this down is cheap now and expensive once towns have adopted records.

8. **Accessibility commitment.** The DOJ ADA Title II web rule binds the towns for their public-facing content — which is the portal you host. If towns rely on you for that conformance, the portal a11y work is a launch blocker rather than a roadmap item, and a VPAT is likely needed before the first paid signature. Related sub-decisions: is a tablet a supported device for running a live meeting (a real responsive redesign vs. a documented minimum-width requirement), and does dark mode exist at all (~200 `dark:` declarations currently ship against a light-only theme).

9. **Refactor budget before feature work.** The four god components, the missing data layer and the untyped Supabase client are the mechanism behind most findings in Themes B and C. Options: (a) type the client and build `hooks/data/` for the three highest-churn entities before any Phase 2 feature; (b) fix bugs in place and accept that the collisions recur; (c) full extraction first. Option (a) is the smallest change that stops the bleeding — typing the client alone would have caught most of the confirmed schema drift in one pass.
